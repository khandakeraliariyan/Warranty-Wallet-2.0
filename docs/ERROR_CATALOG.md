# API Error Catalog

The API centralizes failure mapping in `backend/src/utils/errorMapper.js` and `backend/src/middlewares/error.middleware.js`. This guide describes expected client behavior without exposing provider internals.

## Response shape

```json
{
  "success": false,
  "message": "Readable error message."
}
```

Clients should primarily branch on the HTTP status and use `message` for display. They should not parse provider-specific words from the message.

## Authentication errors

### Missing bearer token

- Expected status: `401 Unauthorized`
- Cause: protected route called without `Authorization: Bearer ...`
- Client action: clear partial app state and navigate to login.

### Invalid or expired Firebase session

- Expected status: `401 Unauthorized`
- Cause: token cannot be verified or is no longer valid.
- Client action: request a fresh Firebase token once; if that fails, sign out.

### Application user not synchronized

- Expected status: `401` or `404`, depending on the route policy.
- Cause: Firebase identity exists without a matching active database user.
- Client action: invoke the synchronization flow before protected requests.

## Authorization errors

### Administrator access required

- Expected status: `403 Forbidden`
- Cause: authenticated user lacks the `ADMIN` role.
- Client action: return to the normal dashboard and avoid retrying.

### Resource does not belong to user

- Expected status: `403` or ownership-scoped `404`.
- Cause: identifier belongs to another user or is outside the permitted asset.
- Client action: remove stale UI state and return to the relevant list.

### Account blocked or deleted

- Expected status: `403 Forbidden`.
- Cause: local account status does not allow application access.
- Client action: sign out and show the account-status message.

## Validation errors

### Invalid JSON field

- Expected status: `400 Bad Request`.
- Cause: missing required field, invalid enum, invalid date, malformed ID, or out-of-range value.
- Client action: preserve form input and display field-level guidance when available.

### Invalid query parameter

- Expected status: `400 Bad Request`.
- Cause: unsupported sort field, direction, report format, status, or date range.
- Client action: reset the invalid filter and retry only after correction.

### Plan limit reached

- Expected status: `400`, `403`, or `409`, according to the service rule.
- Cause: creating another asset would exceed the current plan limit.
- Client action: explain the limit and link to billing.

## Resource errors

### Resource not found

- Expected status: `404 Not Found`.
- Cause: the identifier does not exist, was deleted, or is hidden by ownership scope.
- Client action: return to the list and refresh.

### Duplicate category, brand, user, or provider ID

- Expected status: `409 Conflict`.
- Cause: Prisma uniqueness constraint or idempotent provider identifier.
- Client action: avoid automatic retries; ask the user to choose a different unique value or refresh existing state.

### Invalid lifecycle transition

- Expected status: `400` or `409`.
- Cause: claim, payment, subscription, or asset cannot move from its current state to the requested state.
- Client action: refresh the resource and display its current state.

## Upload errors

### File too large

- Expected status: `413 Payload Too Large` or mapped `400`.
- Message: file exceeds the configured 5 MB limit.
- Client action: reject before upload when possible and suggest compression.

### Too many files or wrong field

- Expected status: `400 Bad Request`.
- Cause: request exceeds upload count or uses an unexpected multipart field.
- Client action: use `files` for multi-upload routes and `file` for single-upload routes.

### Unsupported or spoofed content

- Expected status: `400 Bad Request`.
- Cause: MIME type is unsupported or file signature does not match it.
- Client action: ask for a PDF, JPEG, PNG, or WebP generated by a trusted application.

### Document is locked by claim usage

- Expected status: `409 Conflict`.
- Cause: replacement or deletion would invalidate claim evidence.
- Client action: explain the related claim and require evidence detachment or claim completion first.

## Database errors

### Database unavailable

- Expected status: `503 Service Unavailable`.
- Cause: connection failure, maintenance, or network outage.
- Client action: show a retryable service message with backoff.

### Transaction pool timeout

- Expected status: `503 Service Unavailable`.
- Cause: database concurrency or connection pool pressure.
- Client action: retry after a delay; do not submit multiple parallel duplicates.

### Uniqueness conflict

- Expected status: `409 Conflict`.
- Cause: a unique record already exists.
- Client action: refresh or change the conflicting field.

Raw Prisma error codes and SQL details must never be shown to the browser.

## Firebase provider errors

Expected provider failures include invalid credentials, revoked tokens, disabled accounts, and unavailable identity services. The API maps these to authentication or service errors without returning Firebase Admin internals.

## Cloudinary errors

Upload, replacement, or deletion may fail because of credentials, quota, network availability, or invalid provider IDs. The API should return a safe service error and preserve database consistency.

Clients should not retry uploads automatically without user awareness because the original request may have reached the provider.

## Gemini errors

### Model unavailable

- Expected status: `502` or `503`.
- Cause: configured model does not exist, has been retired, or is temporarily unavailable.
- Client action: allow manual asset entry and preserve the uploaded file selection locally where safe.

### Invalid structured response

- Expected status: `502 Bad Gateway`.
- Cause: provider returned content that cannot be parsed into the expected invoice fields.
- Client action: offer retry and manual entry; never save unvalidated raw output.

### Quota or authentication failure

- Expected status: safe provider error.
- Client action: do not repeatedly retry; administrators should inspect provider configuration and quota.

## Stripe errors

### Checkout creation failed

- Cause: invalid plan, Stripe configuration, customer creation, or provider availability.
- Client action: keep current plan unchanged and show a retryable message where appropriate.

### Checkout is not paid

- Expected status: `400` or `409`.
- Cause: confirmation attempted for an unpaid or incomplete session.
- Client action: return to checkout status rather than granting access.

### Checkout belongs to another user

- Expected status: `403 Forbidden`.
- Cause: session metadata or stored payment owner does not match the current user.
- Client action: reject permanently and do not expose session details.

### Webhook signature invalid

- Expected status: `400 Bad Request`.
- Cause: raw body changed, secret is wrong, or request did not come from Stripe.
- Provider action: Stripe retries according to its delivery policy; operators must correct the endpoint configuration.

## SMTP errors

Email delivery can fail after an application notification is recorded. The system should keep domain state consistent and make the delivery failure observable. A client should not assume an in-app operation failed solely because email could not be sent.

## Rate limiting

- Expected status: `429 Too Many Requests`.
- Cause: client exceeded the API window limit.
- Client action: stop immediate retries and wait before trying again.

## Unexpected failures

- Expected status: `500 Internal Server Error`.
- Client action: show a generic message, preserve unsaved user input, and offer a controlled retry.
- Server action: log the original error through an approved observability channel without secrets or personal document content.

## Retry guidance

Safe candidates for delayed retry:

- Read-only `GET` requests after `503`.
- Idempotent notification reads.
- Provider calls when the API explicitly indicates temporary unavailability.

Do not blindly retry:

- Checkout creation.
- File uploads.
- Resource creation.
- Destructive operations.
- Requests rejected with `400`, `401`, `403`, `404`, or `409`.

For mutations, use an application-specific idempotency key or refresh current state before retrying.
